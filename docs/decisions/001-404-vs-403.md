# ADR 001: cross-tenant access returns 404, not 403

**Status:** accepted (2026-10-09)

## Context

A caller from tenant `bravo` requests `/api/resources/1`, which belongs to tenant `alpha`.
The service must refuse. The question is what the refusal looks like.

- **403 Forbidden** says "this exists, but not for you". Over many requests that turns the API
  into an oracle: an attacker can enumerate which IDs exist in other tenants, how many records
  a competitor has, and when new ones are created.
- **404 Not Found** says "there is nothing here for you", which is true from the caller's
  point of view.

## Decision

- Cross-tenant access to an object returns **404**, with a body byte-for-byte identical to the
  one for an ID that does not exist at all (apart from the echoed request path).
- **403** is reserved for the caller's *own* tenant, when their role lacks the permission
  (e.g. a viewer trying to delete). The caller is entitled to know that object exists.
- Error bodies never include IDs, tenant names or usernames.

## Consequences

- The property tests can assert one simple rule: a cross-tenant request is never 2xx and never
  403; it is always the generic 404.
- Debugging is harder, since logs (not responses) must record the real reason. The audit log
  of denied requests (RBAC phase) covers this.
- This follows the OWASP API Security Top 10 (2023) guidance for API1, Broken Object Level
  Authorization: authorize every object access by the caller's identity, and don't reveal
  object existence across trust boundaries.
